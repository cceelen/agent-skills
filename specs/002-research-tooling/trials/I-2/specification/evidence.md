| S-01 | The guide divides the field into 18 knowledge areas. The operations area covers deployment, operation and support; it asks to plan the operation early, to make the environments from one source as code, and to monitor with telemetry. It says that DevSecOps moves testing and security to the early phases. Availability and service levels are measured against service-level targets. The operations area names rollback, feature toggles and canary releases, and asks the operations engineers to agree the risk tolerance for alerts with the product owners. The construction area names the supply chain risk of dependencies and continuous integration. The testing area names shift-left testing and automated regression tests. The configuration management area names baselines and the software bill of materials. The quality area says to plan quality early and to start verification early, and that the verification tasks are selected by the integrity level of the software. The security area asks for security in each stage of the life cycle, with threat modelling, secure coding rules and static and dynamic security tests. If they are not repaired early, missing requirements can induce cascading rework, and security requirements tend to be overlooked. | Pages 40 (knowledge areas); 43, 46-47 (requirements); 103-104, 107 (construction); 139-140 (testing); 151-162 (operations); 192 (configuration management); 206 (management); 248, 250-251, 255, 257 (quality); 264-268 (security) | C-01, C-02, C-03, C-04, C-05, C-07, C-12, C-13, C-15, C-16, C-18, C-24; section 1 stakeholders, views, contexts, risk dimensions, boundaries | 2026-10-11 |
| S-02 | The working draft has four tracks: Build, Build Environment, Dependency and Source. The Build track has levels L0 to L3: L1 asks for provenance that identifies the output package by its digest and should hold sufficient information to catch mistakes; L2 adds a hosted build platform, and the provenance should be signed with a key that only the platform can use; L3 adds the isolation of runs and keeps the signing secrets from the build steps that the user defines. The Source track has levels L1 to L4: L1 version control; L2 continuous, immutable history and source provenance; L3 enforced technical controls on protected references; L4 a review of changes to protected branches by two trusted persons. The Build Environment track has levels L0 to L3, up to a hardware-rooted attestation of the host. The Dependency track has levels L0 to L3: inventoried, controlled, screened. The verification is an activity of the consumer, or of a package ecosystem or a monitor: it checks the signature, the subject and the builder against expectations; the page names one verifier program as an example. The draft can be modified, replaced or discarded at any time. | S-03 | The framework gives practices in four groups: prepare the organization (PO), protect the software (PS), produce well-secured software (PW), respond to vulnerabilities (RV). It says that early security work costs less than late work, and that a shift to the left can reduce technical debt. The practices are not prioritized; risk, cost, feasibility and applicability should be considered in the decision which practices to use. The tasks ask to create roles and change responsibilities so that they cover all parts of the life cycle (PO.2.1; security roles are in the examples); to get the commitment of the upper management to secure development (PO.2.3); to follow recommended security practices for the tools and toolchains (PO.3.2; a configuration as code is an example); to secure and harden the development endpoints with a risk-based approach (PO.5.2; multi-factor authentication is an example); to store all forms of code and restrict the access to it by least privilege (PS.1.1); to publish integrity verification information for releases (PS.2.1); to make provenance data available, for example as a software bill of materials (PS.3.2); to use risk modelling such as threat modelling for the design (PW.1.1); to decide which features of the compiler and the build tools to use, and to use the approved configurations (PW.6.2; a clean build with warnings as errors is an example); to do code analysis, for example automated at the check-in (PW.7.2); to test executable code, for example with dynamic vulnerability tests in the automated test suite (PW.8.2); to have a vulnerability disclosure policy (RV.1.3). | S-04 | The publication describes DevSecOps as an agile development paradigm for cloud-native applications that uses CI/CD pipelines, and its goal is that the activities of the pipeline from the source to the deployment are not compromised. It says that a software bill of materials is not sufficient for the management of vulnerabilities. Workstations of developers are not trusted as parts of the build. It says that companies should have controls for the assets of the developer environment, such as multi-factor authentication. It asks for checks at the pull and the push, with no approval of the own merge; that a pipeline run for a pull request from outside to a public repository either runs in a sandbox or waits for the approval of a maintainer; for static and dynamic security tests in the pipeline with code coverage reports to developers and security staff; for the detection of secrets and push protection; that the details of vulnerable versions of dependencies can be seen before a merge; for build policies and evidence that is made together with the build; for attestations that are signed and stored safe against changes. Linters and unit tests are among the automated checks. For the deployment it asks for automation in place of manual steps, no manual change at runtime, and the monitoring of drift. The security team should establish a policy for trusted sources of open-source code. It says that the secure design of software and the enterprise management of vulnerabilities are beyond its scope, and it leaves the runtime access control to other documents of its series. It gives no scale with levels. | Pages 10-12 (definition, goal, limits); 13 (bill of materials); 17-19 (developer environment, threats); 21 (open-source intake, security team); 24-26 (build, attestation); 26-27 (pull and push); 28-29 (tests, secrets, dependencies); 30-31 (deployment) | C-03, C-08, C-10, C-11, C-14, C-16, C-19, C-20, C-21, C-22, C-23, C-28, C-29; section 1 stakeholders, views, contexts, boundaries; 3.4 | 2026-10-11 |

| S-08 | The model has five functions (governance, design, implementation, verification, operations) with fifteen practices; each practice has two streams with three maturity levels. | S-09 | The metrics guide names five measures of delivery performance: change lead time, deployment frequency, failed deployment recovery time, change fail rate and deployment rework rate. It gives no levels, and says that the measures apply best to one application or service at a time. The capability for security says that security is the work of all, moves security work into the daily work, and asks for a security review of the design and for security tests in continuous integration. The capability for version control asks to keep all production artifacts in version control. The capability for deployment automation asks for the same deployment process in each environment. The capability for continuous integration asks for automated tests on each commit and a fast correction of a broken build. The capability for test automation says that late feedback makes defects expensive, and gives a start for existing systems. The capability for monitoring asks for alerts that need an action. Trunk-based development asks for a merge at least daily, and warns against heavy and asynchronous review. The capability for change approval prefers peer review to an external approval board, and names the segregation of duties. | S-10 | The book describes the practice at one company. A service level indicator is a measured value of the service; a service level objective is a target for it; the error budget is the permitted unreliability that follows from the objective, and the product management takes part in the setting of the objective. A target of 100% is not correct. Monitoring pages a person on symptoms that users see, and each page needs an action; four signals are latency, traffic, errors and saturation. Release engineering asks for builds that are automated and hermetic, for code review, and to start it early in a project. Before a launch, a checklist examines the architecture and dependencies, the capacity, the failure modes, the steps that are done by hand and the rollout plan; rollouts are gradual with canaries. A production readiness review finds the reliability needs of a service, and an engagement at the design is better than one after the launch. For existing code: tests for the critical code first, a smoke test for each release, and each reported bug becomes a test. | https://sre.google/sre-book/ and below it: introduction (chapter 1); embracing-risk (chapter 3); service-level-objectives (chapter 4); monitoring-distributed-systems (chapter 6); release-engineering (chapter 8); testing-reliability (chapter 17); reliable-product-launches (chapter 27); evolving-sre-engagement-model (chapter 32) | C-01, C-02, C-04, C-05, C-06, C-07, C-15, C-17, C-22; section 1 stakeholders, views, contexts, risk dimensions, boundaries, targets; 3.3 | 2026-10-11 |

| S-12 | The baseline gives controls in eight families (access control, build and release, documentation, governance, legal, quality, security assessment, vulnerability management) on three maturity levels. Level 1 is for each project; level 2 is for a code project with at least two maintainers and a small number of consistent users; level 3 is for a code project with a large number of consistent users. A project can attest itself. | S-13 | The paper gives practices for five stages: source code, materials, build pipelines, artefacts, deployments. It has assurance categories low, moderate and high, and risk environments moderate and high; a high risk environment includes personal data, financial services and critical infrastructure. From the moderate level it asks for: signed commits; the prevention of secrets in commits; automated security scans; a review and approval by at least two persons who are independent of the request, where the author does not approve; branch protection; multi-factor authentication for the access to the repository; the verification of third-party artefacts; a bill of materials of the code, preferably made during the build; scans of dependencies for vulnerabilities and licences; a build pipeline that is defined as code; the signing of each build step; the verification of artefacts and metadata by the client.
